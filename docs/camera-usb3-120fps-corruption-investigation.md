## TL;DR（一分钟结论）

| 主题 | 症状 | 根因 | 修法 | 数据 |
|---|---|---|---|---|
| ffmpeg "APP fields" 报错 | **每帧**都刷（两相机、USB2/USB3 一样） | 相机 JPEG 写空载荷 APP1（`FFE1 0004 0000`），ffmpeg 4.4 解析不了 | **忽略**（良性）；libjpeg/OpenCV 全忽略 | 删 APP1 后错误消失（实测） |
| ffmpeg 实时解码洪水 | `Found EOI before SOF`/`No JPEG data`/`bad vlc`/dts | 120fps 软解过载 + 缓冲覆盖，**只在实时路径** | 换采集方式（不用 ffmpeg） | 文件里没有这些错（离线干净） |
| **真实坏帧（核心）** | USB3@120 录像 ~0.7-2.4% 帧有 `error dc` | **相机编码器在 SS 120fps（实际 130fps）下间歇故障**，熵数据局部坏 | 固件更新 + **迁 USB2@30** | 见下方量化 |
| 帧率 vs 端口 | USB2@120 干净、USB3@120 坏 | 损坏跟 **USB3/SS 链路**绑定，不是帧率 | 同上 | 四格表实测 |
| 为什么 USB3 帧更大 | USB3@120 帧中位 169KB/均 252KB vs USB2@120 134KB | **固件按链路带宽自适应量化**（SS 细量化 q11、HS 粗量化 q15） | 无控件可改，但管线 q90 重编码不受影响 | DQT 逐帧实测 |
| USB2 线强制 HS | USB3 口 + 4 芯线 → 480M | 线无 SS 差分对，设备协商到 HS，用 HS 描述符 | **换 USB2-only 线 / USB2 hub** | `lsusb -t` 5000M→480M |
| xHCI 脏状态 | 整机相机全停摆（base 0.1fps） | `pkill -9` 杀流进程 → xHCI 传输环脏 → 控制器级错乱 | **整机重启**（软复位无效） | dmesg `Event TRB ... no TDs queued` |

## 结论：最终修好，别用 USB2 线了

2026-09-24 厂商固件更新后，两台 WN 相机在 USB2/USB3 都枚举 MJPG 720p **30/60/120 三档**。
用户把两台 WN 全部迁到 USB2 口、D435i 挪到 USB3 口，`label_aliases` 按新 by-path 更新。
**全链路验证通过：三路全部 30fps、0 坏帧**，base 保持 1080p30 无需降档（见 §7）。

## 一、ffmpeg 报错分三类：只有一类是真损坏

同一段 USB3@120 录像，ffmpeg 报的错误其实是**三种完全不同的东西**，先分开：

### ① `unable to decode APP fields` —— 良性，每帧都报，两相机一样

- **现象**：USB2"正常"的相机 442 帧也 100% 报；单帧提取后照样报。
- **根因**：相机每帧 JPEG 头写一个**空载荷 APP1 段**：`FF E1 00 04 00 00`（只有 2 字节 `00 00`）。
  ffmpeg 4.4 的 `mjpeg_decode_app`（`libavcodec/mjpegdec.c`）解析它失败即打 ERROR。
- **实锤**：把单帧里的 APP1 删掉 → 错误消失；改成 6 字节零仍报（长度还是 4）。
- **结论**：**不是损坏**，是相机 JPEG 格式的怪癖。libjpeg/OpenCV 完全忽略。以后看 ffmpeg 日志
  过滤掉：`grep -v "APP fields"`。

### ② 实时解码洪水 —— 只在 `-f v4l2` 实时路径，文件里没有

- **现象**：`ffmpeg -f v4l2 ... -f null -` 实时 120fps 解码报 `Found EOI before any SOF`/
  `No JPEG data found in image`/`bad vlc`/`non monotonically increasing dts`。
- **根因**：Jetson 软解 720p@120 过载 + ffmpeg V4L2 输入层缓冲被覆盖 → 帧边界错位。
- **实锤**：同一相机 v4l2-ctl 采下来的文件**离线解码这些错误几乎消失**——文件本身没这问题。
- **结论**：实时采集路径的伪影，与文件数据无关。

### ③ `error dc` / `overread` / `error y=x` —— **真实熵损坏**（核心问题）

- 帧内 SOS 之后的熵编码数据局部损坏，Huffman 解码失步到下一个 RST 标记。
- 表现为图上 **1-3 行 MCU 的横向坏条带**；帧完整（SOI→EOI 齐全）、非截断、标记完好。
- 逐帧坏点位置随机（MCU y=4~88 都有）、与帧大小无相关。
- 这是唯一需要解决的真问题。

## 三、根因归因：损坏跟 USB3/SS 链路绑定，不是帧率

### 四格表（全用有效数据）

| | USB2 口 | USB3 口 |
|---|---|---|
| **30fps** | 干净（0/442, 0/300） | **固件拒绝**：`--set-parm=30` 被打回 120 |
| **120fps** | **干净**（0/400 亮场景） | **坏**（12/1563, 5/400） |

- 同帧率（120）、同机、同时刻：USB2 0 坏帧 vs USB3 1.25% → **损坏绑定 USB3/SS 链路**。
- USB3 口固件拒绝 30fps → **软件手段在 USB3 上拿不到 30fps**（枚举层只有 120）。

### 为什么是相机编码器自产（不是 USB 丢字节）

1. UVC 传输有 **CRC16 校验**，出错帧默认被 uvcvideo 驱动**丢弃**（`nodrop=0`）。
   能"完整送达"的坏帧 = 传输无错 = 相机编码器自己写坏的。
2. v4l2-ctl 是最干净的采集方式，采出来的文件照样有 error dc（`test_v4l2_15s` 有 69 个错误行）。
3. dmesg 无 USB 传输错误。

### 编码器为什么过载

- 相机在 SS 模式**实际超发 ~130fps**（超标称 120）。
- 每秒编码工作量 = 帧率 × 每帧工作量：

| 模式 | 帧率 | 量化 | 每秒负载 | 结果 |
|---|---|---|---|---|
| USB2@30 | 30 | q7（中） | 低 | 干净 |
| USB2@120 | 119 | q15（粗） | 低 | 干净 |
| USB3@120 | **130** | **q11（细）** | **高** | ~1% 坏帧 |

- **结论：损坏 = SS 120fps 模式"高帧率 × 高单帧工作量"把编码器推到极限的偶发故障**。
  不是"帧大"导致（同大小帧在 30fps 下干净），是"帧大"与"坏帧"同源于 SS 模式的编码档位。

## 四、为什么 USB3 帧更大（编码损失/质量差异）

### DQT 量化表逐帧实测（同一固件、亮场景背靠背）

| | 亮度 | 细节 | DQT0[0] 中位 | 帧中位 | 帧平均 |
|---|---|---|---|---|---|
| USB2@30 | 95.5 | 2386 | **7（细）** | 187KB | 188KB |
| USB2@120 | 102.6 | 2335 | **15（粗）** | 134KB | 135KB |
| USB3@120 | 106.9 | 2513 | **11（中）** | 169KB | **252KB**（胖尾 554KB）|

- 场景接近（亮度/细节一致），量化表明显不同 → **固件按链路带宽自适应量化档位**：
  SS（5Gbps）带宽充裕 → 细量化（更高原始质量、更大帧）；HS（480Mbps）→ 粗量化省字节。
- **相机侧无控件可改**：`v4l2-ctl -L` 只有亮度/对比度/曝光等，**无 JPEG 质量/帧率控件**。
- **对训练数据无影响**：`collect_tap` 把每帧统一重编码成 **quality-90 JPEG**，训练数据质量固定，
  不继承相机原始帧大小。所以"USB3 帧更大"只影响原始采集吞吐，不影响数据质量。

## 五、采集方式差异：ffmpeg / OpenCV / v4l2-ctl 吞吐对比

### 实测（USB3 video9，8 秒）

| 消费者 | 帧数 | 捕获率 | 每帧额外开销 |
|---|---|---|---|
| v4l2-ctl | 940/960 | **98%** | 无（DQBUF→写盘→QBUF） |
| webcam_source（OpenCV） | ~101fps | ~84% | libjpeg-turbo 解码 |
| ffmpeg `-c:v copy` | 766/960 | **80%**（更长录音仅 59.6%） | mjpeg demuxer 头解析 + avformat mux + I/O |

- **ffmpeg 损失最大**：`-c:v copy` 不解码但每帧仍跑 demuxer 头解析 + avformat 封装 + 磁盘 I/O，
  120fps 下每帧 8.3ms 预算被超 → 驱动 4 缓冲被占满 → 丢帧；实时解码再加软解直接洪水。
- **webcam_source 也丢 ~16% 源帧**，但对 30fps 目标无所谓：源 ~100fps 有 3 倍余量，投递门只取
  最新帧，丢帧不影响 30fps 交付。
- **关键**：三种采集方式采到的是**同一个坏流**——采集方式既不产生也不修复损坏，坏帧在相机输出里。

## 六、USB2 线强制 HS（把 USB3 相机降到 480M）

### 原理

- USB3 设备按**协商出的链路速度**选描述符：SS（5Gbps，9 芯线含 SS 差分对）→ SS 描述符
  （只有 120fps + 细量化）；HS（480Mbps，4 芯线）→ HS 描述符（30/60/120 + 粗量化）。
- **USB2-only 线（4 芯、无 SS 对）插在 USB3 口** → 设备物理上够不到 SS → 协商 HS → 用 HS 描述符
  → 30fps 可选。**物理口位不变，by-path 不变，label_aliases 零改动**。

### 识别 USB2-only 线

| | USB3 线 | USB2-only 线 |
|---|---|---|
| 线身 | "SS" 标志 | 无 |
| 插头内芯 | **蓝色** | 黑/白/灰 |
| 芯数 | 9 | 4 |

- 验证：`lsusb -t` 右腕从 `5000M` 变 `480M`；`--list-formats-ext` 出现 30fps；`--set-parm=30` 生效。
- ⚠ **实测踩坑**：声称"换了一根线"但 `lsusb -t` 还是 5000M、还是只有 120fps → 换的线是 USB3 线。
  **只要还协商出 5000M，那根线就带着 SS 对，不是 USB2 线。**

## 七、xHCI 脏状态坑（`pkill -9` 杀流进程的代价）

### 症状与根因

- 用 `pkill -9` 强杀正在 streaming 的 v4l2-ctl → xHCI 传输环（transfer ring）留下脏状态 →
  **控制器级错乱**，波及同控制器所有设备（Realsense 和 WN 同在一棵 xHCI 树）。
- dmesg 实锤：`tegra-xusb 3610000.usb: WARN Event TRB for slot N ep 2 with no TDs queued?`
- 后果：全相机停摆（base 0.1fps、right 1fps、left 0fps），cv2 select() 超时。

### 为什么软件复位都无效

- uvcvideo 解绑/重绑：只在内核驱动层，不动 xHCI 传输环。
- `authorized` 开关：软件去授权，不切物理电源。
- 物理拔插单个设备：只复位该设备，不动控制器。
- **唯一有效：整机重启**（重初始化 xHCI 控制器）。

### 教训

**排查相机/流媒体时不要 `pkill -9` 正在采集的进程**——用 SIGINT（`kill`）让 V4L2 走正常
release 路径（`uvc_video_stop_transfer` 会清理 URB）。整机 USB 卡死优先怀疑这个。

## 八、最终解决与验证（2026-09-24）

### 变更

1. **厂商固件更新**：两台 WN 相机在 USB2/USB3 都枚举 MJPG 720p **30/60/120 三档**。
2. **迁址**：两台 WN 全部移到 USB2 口（right_wrist=usb-0:2.2.2→video8、left_wrist=usb-0:2.2.3→video6），
   D435i 挪到 USB3（usb-0:1.4，彩色节点 1.4:1.3→video4）。
3. **label_aliases 更新**：base→`1.4:1.3`、left_wrist→`2.2.3`、right_wrist→`2.2.2`。

### 验证数据

**固件回归（两台 WN 720p30）**：

| 相机 | 帧数 | error_dc |
|---|---|---|
| left_wrist (2.2.3) | 200/200 | **0** |
| right_wrist (2.2.2) | 200/200 | **0** |

**Test A：base 1080p30 + 全链路**：

| 相机 | driver-side | collect | Corrupt JPEG |
|---|---|---|---|
| base (1080p) | 27.3 | **30.041 Hz** | 0 |
| left_wrist | 27.8 | **30.029 Hz** | 0 |
| right_wrist | 27.8 | **29.965 Hz** | 0 |

**Test B：base 720p30 + 全链路**：

| 相机 | driver-side | collect | Corrupt JPEG |
|---|---|---|---|
| base | 28.0 | **29.991 Hz** | 0 |
| left_wrist | 27.8 | **29.983 Hz** | 0 |

**端到端 collect 输出**：三路各 40 帧，100% 解码、0 条带伪影。

### 结论

- **坏帧问题随固件更新 + USB2 迁址彻底消失**。
- **base 保持 1080p30，无需降档 720p**：此前 base 19-26fps 是旧固件右腕 120fps 吃 CPU 拖的；
  现右腕 30fps + Realsense 挪 USB3 后，base 1080p30 稳定 30Hz。
- 当前配置可直接采数/推理，链路健康。

## 九、可复用排查清单（下次遇到"相机出坏帧/掉帧"）

1. **先分 ffmpeg 三类错误**：APP fields（良性，忽略）/ 实时洪水（换采集方式）/ error dc（真坏）。
2. **确认场景有效**：录制样本先看亮度/细节（亮度 <50 或细节 <500 的样本不可用于损坏评估）。
3. **做四格表对照**：把"链路（USB2/USB3）× 帧率（30/120）"四个组合各录一段，用
   `ffmpeg -f mjpeg -i x.mjpg -f null - 2>&1 | grep -c "error dc"` 计数。
4. **判断谁产生坏帧**：查 `dmesg` 有无 USB/URB 错误；无 → 相机编码器自产，换链路/固件/迁址。
5. **查量化/质量差异**：逐帧读 DQT（`FFDB` 段），看是否动态量化、是否随链路变档。
6. **采集效率对比**：ffmpeg 最差（avformat 开销）、v4l2-ctl 最好、OpenCV 居中——但对 30fps
   目标三者都够，别为吞吐换采集器。
7. **强制 HS**：USB2-only 线（内芯非蓝、无 SS 标志）插 USB3 口，`lsusb -t` 确认 480M。
8. **绝不 `pkill -9` 采集进程**；要杀用 SIGINT，整机 USB 卡死先重启。
