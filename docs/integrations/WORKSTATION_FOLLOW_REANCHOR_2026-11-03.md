# 持续跟随与多映射重锚修复

日期：2026-11-03，基线 e183d36。代码与本记录随本次提交归档；实体 Quest/CR5 和 Linux ROS 现场验收待执行。

## 实际根因与门控修复

Web“持续跟随 · 无按住使能信号”保存 `deadman: ""`，编译器保留空字符串。旧 BindingEngine 仅对 None 放行，空字符串进入后续判断，无法匹配端口，最终只能借 operator_hold=True 才运动。这解释了用户实测“持续跟随仍需按住 grip”。上轮审查只检查字段缺失，遗漏页面实际保存的空字符串。

现在 None 和空字符串都表示持续跟随，不扩大到接受其他无效类型。显式指定 quest.right_hold 时保留按住判断及原 operator_hold 辅助使能。持续跟随松开 grip 后仍跟随，必须使用 Web 暂停/停止；再次按 grip 仍重定零点。裸手捏合不自动开始全局遥操。

这属于公共 BindingEngine 修复，不增加 CR5 专有门控。已有保存配置不必重写；重建并重启服务后生效。同步更正 cr5_vr.md、cr5.md、CR5 包 README，此前笼统声称“无 deadman 也被强制 hold”的解释不再成立。

## 多映射冷启动

e183d36 的构造后重读输入是必要修复。但每个映射构造后立即重锚，先完成的锚点仍可能等待其他慢控制器而超龄。隔离双映射复现中两者均 ACK，最终仍报“重锚输入在确认前过期”。

本次改为：冻结输出并确认激活 → 有界工作线程完成全部控制器构造 → 每个输入实例统一读取最新快照并采集最新设备反馈 → 执行重锚 → 收齐 ACK 后严格复检、原子提交。

保留原 3 秒总期限、绑定输入/反馈时效、0.02 关节单位漂移拒绝。既校验重锚种子，也校验冻结时反馈，避免分阶段放宽累计漂移。构造和重锚分别持有 Future；取消或超时清理当前阶段的结果，迟到构造结果关闭控制器，不能获取运动权限。控制器重锚本身过慢仍会失败，没有取消时效检查。

没有复用可变 IK/滤波状态，也未引入新的模型缓存。预热不可变资源可留作后续性能优化。
