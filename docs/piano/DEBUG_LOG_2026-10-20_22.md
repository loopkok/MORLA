## 2026-10-21：反馈初始化、维护与 SDK 误写事件

### 建立会话、复位和使能的状态拆分

症状包括只有驱动状态而没有关节反馈、复位按钮灰色、急停复位与使能相互阻塞，以及已有 XHand 发布者占用。

处理：双臂维护就绪不再依赖双手位置反馈；无力反馈初始化由操作员明确触发；复位需要确认新的控制器状态，不能用服务请求接受代替完成，也不自动进入演奏。明确区分 CAN 初始化、急停复位、反馈检查、控制权和位置运动。

### 必须保留的 SDK 诊断误写记录

历史诊断探针曾把 SDK 私有 `write_to_device` 当成状态请求，实际发送 0x05，并出现 `save to flash ok`；既有事件记录称两手各请求 60 次。另有 `read_state(..., true)` 会重发内部命令缓存，因此不能称为纯只读。

处理：停用并归档危险探针；后续读参数探针加串口写白名单；位置/无力报文离线验证在传输前截获。没有事前标定快照，不能证明误写没有影响，也不能自动恢复出厂标定。用户后续自行在厂商上位机重新标定。

完整记录：[SDK 诊断误写记录](sdk-probe-incident.md)。本轮日志整理不修改设备 Flash，也不撤销该事件。

### 小角度负值与软件手姿参考

某些手指实测略小于目标下限，导致运动接管拒绝。引入 `start_reference_rad`，仅对匹配已保存参考的微小边界偏差生成最近合法控制目标，保留原始实测。参考必须属于当前会话加载配置；它不是硬件编码器零位。

证据：[软件手姿参考记录](hand-reference-calibration-20261021.md)。该历史参考不因后续关闭到位检查而失效；边界接管和目标限位检查仍独立存在。

- 右手：`/dev/serial/by-id/usb-FTDI_USB-RS485-WE_FTAAUYUK-if00-port0`。

SDK 内部 L/R 标签不是机械臂安装归属的可靠判定依据；没有因此改设备手型或 Flash。

来源和边界：[手册限位说明](xhand-manual-limits-20261022.md)。部署报告：服务器 `/home/loopkok/MORLA/.morla_piano/diagnostics/manual_limits_verification_20261022.json`。

### 机械臂保持目标连续性和 J7 报文兼容

症状：点动时先下坠，再调整；工作位第 1 段反复出现约 60°误差，而页面 J7 曾显示 −60°。

处理：连续控制时保持已有命令目标，避免每次点击用跟踪误差重新播种全部保持关节；明确控制域切换和使能状态确认。针对当前固件的钢琴驱动启用 `native_j7_first=True`：原生 J 批次先发送 J7 帧，再发送其余三帧，增加短间隔，保留 SDK 编码与原四段目标。钢琴流式通道使用 `stream_position_mode="j"`。

证据包括离线 SDK 内存报文、被动 CAN 记录、ROS fake 流程，以及用户明确报告“现在到工作位没问题”“现在运动都可以了”。固件内部触发机制仍属推断，不表述为厂商确认结论。

### 到位、按下确认、跟踪误差分开处理

1. 普通到位容差从 0.025 rad（约 1.432°）改为 3°，Web 上界同步支持精确 3°。
2. 按下确认曾另有 `min(0.02, arrival_tolerance_rad)` 和 0.3 秒等待，导致实际按下仍报“尚未实测按下”；统一读取配置，单指测试先等待确认再保持和抬起。
3. 引入可恢复的 `MotionConfirmationError`。反馈健康时中止操作、保持臂控制并尝试抬指；若恢复阶段出现反馈或驱动故障，仍升级急停。原生 J 轨迹故障仍需要硬件停止，不能把全部错误都当成普通容差失败。
4. 应用户要求，先关闭右手、再关闭左手 `arrival_check_enabled`。这会跳过手部目标到位与按下位置确认，保留等待间隔、读数、SDK 状态、目标限位、控制权和硬件故障检查；日志注明未实测确认。
5. 应用户要求，将共用 `max_tracking_error_rad` 从 0.15 rad 改为 30°。此项同时影响机械臂与手部使用它的跟踪检查，不是只改双手。

关闭到位检查不修改硬件标定，也不解除负值接管参考检查。较大的软件容忍范围不证明琴键已按下。

### 红灯、复位无新状态和无 CAN 帧

一次现场故障中双臂红灯，复位报告 `reset was sent but no fresh controller status returned`。只读检查时两接口 UP、1 Mbps，连续约 3 秒两侧均为 0 个接收帧，驱动缺关节角和法兰反馈。

核对实际安装的 pyAgxArm：Web 已调用 `robot.reset()` 并请求恢复状态推送；未发现独立 `clear_error()` / `clear_fault()`。SDK 调用返回不能替代新鲜控制器状态，未增加伪“清错成功”按钮，也未放宽使能门槛。

后续用户完成了歌曲播放，但缺少厂商错误码或确定的恢复过程，不能据此宣称已查明红灯根因。

## 2026-10-22：Web 操作流程的多次修正

### 首次准备与单侧标定

- 单侧“沿 MORLA 到工作位”只对所选侧执行和判断，避免另一侧误差阻塞。
- Web“按当前保存参数准备”和演奏页“移动到初始位”统一为：抬指 → 双臂 MORLA 四段轨迹 → 保存工作位 → 保存演奏零位。
- 四段路径完成后重新读取当前位置，最后一段不再从四段路径开始前的旧位置插值。
- CLI 的普通 `Engine.prepare()` 仍是直接回演奏零位；四段路径由 Web 的 approach 回调提供。

### 浏览器心跳

先由空闲短超时改为 180 秒，后因后台标签页冻结仍掉线，取消空闲浏览器心跳期限。运动、演奏、维护期间继续使用 6 秒浏览器 watchdog；服务器/worker 和底层控制权心跳继续独立运行。

返回页面重检控制权，不自动恢复旧动作；新运动前要求新鲜浏览器心跳。正常关闭/刷新页面仍请求释放，显式断开仍有效。空闲长期保留需要操作员结束使用时主动释放设备。

### 回起始位：两版行为不可混淆

- 初版接入原生 HOME：第4→3→2→1点，再回 `[0,85,0,0,0,0,0]°`。
- 用户后续改为钢琴专用回位：抬指 → 各自演奏零位 → J4=95° → J1=0° → J2=60° → `[0,85,0,0,0,0,0]°`。
- 左右符号约定为 `(-1,+1,-1,+1,-1,-1,+1)`；本路线 J2、J4同号，零位不镜像重算。
- 最后一段 J4 的插值在总时长 80% 处完成，同时重新计算整段时长以保持最大速度约束。这是命令轨迹安排，不是已测得实体 J4 一定提前到位。
- 只替换钢琴按钮流程，MORLA 原生 HOME 服务保留；全部阶段先验限位，停止/故障后不继续下段。

### 演奏进度与再次演奏

新增服务器 `playback` 状态：曲名、时长、已用时间、动作/音符计数、当前动作、完成标志。播放中低于100%；完成后100%；停止/故障冻结；重新准备清除上次进度。计数是调度/指令进度，不是声音或键盘接触传感器确认。

最初“重新准备并演奏”重复执行了四段路径。经用户纠正，最终行为是：演奏完成位置抬指 → **直接回保存的双臂演奏零位** → 从头播放所选曲谱。支持换曲后预检再重播。

`replay_direct_allowed` 只允许演奏结束，或仍处演奏上下文的正常停止。已回起始位、手动标定和故障状态不能借此绕过首次准备。按钮不可用时显示原因。
